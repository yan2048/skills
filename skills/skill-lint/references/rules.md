# 规则说明与反例

本文件解释每条规则的取舍理由。需要判断某条 WARN 该不该修时，先看这里。

## 为什么 E 级只卡「结构性」问题

一条 error 意味着 skill 可能**根本无法被加载或路由**，修它不需要判断力：

- `E002` frontmatter 缺失/未闭合：WorkBuddy 依赖 frontmatter 读取 `name`、`description`，解析失败等于 skill 不存在。
- `E003`/`E006`：`name` 是 skill 的身份，`description` 是 AI 路由的唯一依据，二者缺一不可。
- `E005` name 与目录名不一致：用户按 README 的目录路径去找，和 AI 按 name 匹配，会指向两个不同的东西。后续改名、引用、软链都会出错。

## 为什么结构章节只报警告

不同 skill 的合理结构确实不一样：

- 模板类（如 `example-skill`）要讲「怎么写」，不需要「何时使用」；
- 纯知识型 skill 可能只有一份「字段字典」；
- 一次性脚本型 skill 可能只有「命令 + 参数」。

强行统一会逼着作者写废话。所以「何时使用 / 工作流程 / 约束」只作为**推荐骨架**提示，`--strict` 时才升级为失败 —— 是否启用严格模式，由仓库维护者按当前阶段决定。

## description 的三条边界

`description` 是投入产出比最高的一行文字，也是最容易写坏的：

**W001 过短**

```yaml
# 反例：AI 不知道什么时候该用它
description: 处理报表。
# 较好：场景 + 对象 + 关键词
description: 审查数据报表指标口径是否一致。当需要核对同名指标在多个报表中的定义、发现同环比异常口径差异时使用。关键词：口径、指标定义、报表对账。
```

**W002 过长**

超过 200 字符后，往往塞进了实现细节（「本 skill 会先读取 A 再调用 B」）。这些属于正文，不属路由依据，留在 description 里只会让匹配信号变模糊。

**W003 缺触发标记**

AI 路由靠语义相似度，但显式的「关键词：xxx」能给同义词兜底 —— 用户说的是「对账」「口径」，而不是你标题里的「一致性检查」。写 skill 时想一遍：**用户会用什么词描述这个需求**，把这些词放进 description。

## 空章节（W006）

```markdown
## 工作流程

## 约束
```

标题建好了但没写内容，通常是草稿状态被提交了。空章节比不写更糟：AI 会认为「这一步没有要求」，从而自由发挥。

## 不做的事

以下判断留给人工 review，脚本不介入：

- 流程步骤是否真的可执行（是否给了具体命令、参数）
- 示例代码能否跑通
- 约束是否覆盖了真实风险（误删、越权、外发）
- 与其他 skill 的职责是否重叠
